# 云端签名部署修复记录（2026-10-11）

> 主题：P3 授权响应 HMAC 签名在 `shouquan.frameweave.top` 路径未生效的根因与完整修复
> 关联：`.agent-teams-read/p4-report.md` §8 ｜ 影响端：客户端 fail-closed 验签
> 状态：✅ 已修复并验证

## 1. 背景

P3 加固后，云端 `/api/auth/*` 响应带 HMAC 签名（`signature` 字段，`FRAMEWEAVE_VERIFY_SECRET` 密钥），
客户端 `cloud_gateway.cloud_verify` 强制验签（fail-closed：无签名/签名不符/nonce 不匹配一律拒绝）。

但用户在 `shouquan.frameweave.top`（Cloudflare 代理）登录时仍被拒签，表现为 verify 响应无 `signature`。

## 2. 根因

**P3 签名版 `cloud_server.py` 在 t4 部署时只发到了旧服 `154.36.178.119:8789`，漏发了韩国新服
`43.108.23.200`（`shouquan.frameweave.top` 的 CF 回源目标）。**

- CF 路径请求 → 韩国新服 8789 → 仍是旧版无签名服务 → verify 响应无 signature
- 客户端 fail-closed → 拒签 → 登录失败
- Cloudflare purge cache 只是清边缘缓存；**回源目标本身没签名版，purge 也无济于事**（§5.1 记为"CF 缓存"，是表象）

## 3. 修复动作

| 步骤 | 操作 | 证据 |
|---|---|---|
| ① | Cloudflare 控制台 `Caching → Purge Cache → Purge Everything` | 用户已操作 |
| ② | sftp 上传本地签名版 `backend/cloud_server.py` → 韩国新服 `/opt/frameweave-cloud/cloud_server.py`（先备份 `backups/<ts>/`） | `sign_auth_resp` grep 命中 2 处 |
| ③ | 韩国新服 `py_compile` + `systemctl restart frameweave-cloud` | COMPILE_OK + active |
| ④ | VERIFY_SECRET 一致性核查 | 韩国新服 `cloud.env` 无该键 → 用代码默认 `fw-verify-secret-2026`；客户端同默认 → 一致 |
| ⑤ | 公网 CF 路径验证 | 响应含 `req_nonce` 回显 + `signature` |

## 4. 验证结果（公网 CF 路径）

```
POST https://shouquan.frameweave.top/api/auth/verify
{"token":"probe","nonce":"cf-check-003"}
→ HTTP 200 {"ok":false,"reason":"token 无效","req_nonce":"cf-check-003","signature":"37f277b1..."}
含 signature: True ✅
```

## 5. 教训 / 运维要点（后续部署注意）

1. **多目标部署必须全覆盖**：更新云端代码时，凡是被客户端可达的服务器（旧服直连 + 韩国新服 CF 回源）都要同步部署；可用 `scripts/update-cloud-auth.ps1` 逐台执行，或维护统一部署清单。
2. **签名密钥一致性**：`FRAMEWEAVE_VERIFY_SECRET` 客户端与云端必须一致（当前同默认 `fw-verify-secret-2026`）；若未来轮换，须**同时**更新客户端打包配置与所有云端 `cloud.env`，否则 fail-closed 会误拒。
3. **发布前核查**：`shouquan.frameweave.top/api/auth/verify` 必须带 `signature` 字段（本记录 §4 命令可复现）。
4. **CF 缓存**：API 动态响应一般不被 CF 缓存；但若改动服务端响应结构，建议 purge 一次兜底。
